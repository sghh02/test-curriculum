# 教材・スプレッドシート・提出導線を確認する

## この章のゴール

- 課題で使う Drive 配布物の役割を説明できる
- テストケースのコピー運用を理解できる
- 提出までに必要な記録先と導線を把握できる

## 基本方針

このカリキュラムでは、媒体を次のように分けます。

- この教材: 学習の進め方、環境準備、提出ルール
- Drive: APK、設計書、スプレッドシート、参考資料
- Backlog: バグ起票

ここでいう `この教材` は、今あなたが学習画面で読んでいる章本文のことです。
学習の順番や手順説明はこの教材で確認し、実際の APK やスプレッドシートは Drive で開きます。

実施の主役はスプレッドシートです。
現場に近い運用を体験するため、課題1 と課題2 の記録は Google Sheets を中心に行います。
不具合報告は Drive ではなく、[TESTCURRICULUM プロジェクト](https://convi0310.backlog.com/projects/TESTCURRICULUM) を使います。
この URL を開けない場合は、その時点で作業を止めて講師へすぐ連絡してください。

## それぞれの役割

### `結合テスト`

結合試験の実施で使います。
主に次を参照します。

- `apk > app-debug.apk`
- `テストケース > IT1`
- `テストケース > IT2`
- `課題1：設計書`

`テストケース` フォルダは配布用の正本です。
開始時は、このフォルダを自分の Google Drive に丸ごとコピーしてから作業します。

運用ルールは次の通りです。

- 講師から別指示がない限り、`IT1` を先に実施し、その後に `IT2` を実施する
- 課題1 の完了条件は、対象シートの実施結果、必要なエビデンス、必要に応じた Backlog 番号がそろっていること
- エビデンスはテスト中に取得したスクリーンショットなどを残すためのもので、実際の保存先は受講者自身の Google Drive の `マイドライブ` に作成した専用フォルダとする

### `単体テスト`

単体試験の設計で使います。
主に次を参照します。

- `課題2：設計書`
- `テストケース`
- `参考資料`
- `テスト計画書`

`テストケース` には配布用の単体試験紙が入っています。
対象画面に合うシートを選び、自分の Google Drive にコピーして使います。

### `Backlog`

課題1 で不具合を見つけた場合に使います。
起票後は、実施シート側にも起票番号を残します。
起票先は [TESTCURRICULUM プロジェクト](https://convi0310.backlog.com/projects/TESTCURRICULUM) です。
この URL を開けない場合は、その場で作業を止めて講師へすぐ連絡してください。

Backlog で実際にやることは次の 5 つです。

1. プロジェクトを開く
2. 新しく課題を追加する
3. 課題種別を `バグ` にする
4. 件名と本文を入力して保存する
5. 発行された課題番号を実施シートの `バグ票番号` に戻す

課題番号は、たとえば `TESTCURRICULUM-123` のような形で表示されます。

開始前に、少なくとも次を確認してください。

- 課題種別
- 優先度の付け方
- 担当者の扱い

起票ルールも先に固定します。

- 課題種別は `バグ` を使う
- 件名は `[結合テスト][ケースID][画面名] 事象` の形で書く
- 優先度は「進行不能なら高め、回避可能なら中以下」を目安にする
- 担当者は講師指示がなければ空欄でよい

起票するときの流れを、実際の記入順で書くと次の通りです。

1. `TESTCURRICULUM` を開く
2. `課題の追加` から新しい課題を作る
3. 課題種別で `バグ` を選ぶ
4. 件名に `[結合テスト][ケースID][画面名] 事象` を入れる
5. 本文に `事象 / 再現手順 / 期待結果 / 実際結果 / 補足` を書く
6. 必要なら優先度を付ける
7. 保存したあと、課題番号をスプレッドシートへ戻す

大事なのは、**Backlog に起票して終わりにしないこと**です。
必ずスプレッドシートの対象行にも課題番号を残し、あとから追える状態にしてください。

## スプレッドシートの使い方

### 1. 配布フォルダ・配布シートを直接編集しない

配布されたフォルダやシートは見本または配布用の正本として扱います。
必ず自分用にコピーしてから作業してください。

### 2. 自分用コピーの名前を決める

次のような名前で統一します。

- 課題1: Google Drive の `マイドライブ` 直下に `課題1_結合試験_<氏名>_YYYYMMDD`
- 課題2: Google Drive の `マイドライブ` 直下に `課題2_単体試験_<氏名>_YYYYMMDD`

`My Drive` は、Google Drive の `マイドライブ` のことです。
共有フォルダではなく、自分の Drive 領域にコピーして作業します。

課題1 では、共有 Drive の `結合テスト > テストケース` を上記の名前で丸ごとコピーし、その中の `IT1` と `IT2` を自分用シートとして使います。

### 3. シートに残す内容を理解する

課題1 では、少なくとも次を残します。

- ケース ID
- 画面または機能
- 前提条件
- 操作手順
- 期待結果
- 実際結果
- 判定
- エビデンス名
- バグ票番号

課題2 では、少なくとも次を残します。

- 対象画面
- 観点
- 前提条件
- 入力条件
- 手順
- 期待結果

## エビデンスと提出の考え方

### エビデンス

課題1では、テスト中に取得したアプリのスクリーンショットなどを残すために、自分の Google Drive に次の名前で保存先フォルダを 1 つ作ってから進めます。

- Google Drive の `マイドライブ` 直下の `課題1_エビデンス_<氏名>_YYYYMMDD`

スクリーンショットの名前は、シートのケース ID と対応づけます。

例:

- `IT1_001.png`
- `IT1_001_1.png`
- `IT1_002.png`

### 提出

このカリキュラムでは、最終的に次を提出対象として扱います。

- 課題1 の `IT1` 自分用シート URL
- 課題1 の `IT2` 自分用シート URL
- 課題1 のエビデンスフォルダ URL
- 課題2 の自分用シート URL
- 必要に応じてバグ票番号
- PR URL

`PR` は `Pull Request` の略で、提出内容をレビューしてもらうための提出ページのことです。

課題1 の完了条件は次の 5 点です。

- 自分用にコピーした `テストケース` フォルダ内の `IT1` と `IT2` の対象範囲を実施している
- 実施シートに判定が入っている
- 必要なエビデンスが保存されている
- 必要に応じて Backlog 番号が戻されている
- PR に提出情報がまとまっている

## よくあるミス

- 配布シートを直接編集してしまう
- 画面設計書を見ずに感覚で判定する
- エビデンス名とケース ID が対応していない
- Backlog の起票先を確認しないまま作業を始める
- バグを見つけたのにシート側へ起票番号を戻さない
